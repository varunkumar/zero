# M8.5: Zero IDE Polish

Status: Approved

## 1. Scope

Scope is defined in `2026-08-17-m8-zero-ide-design.md` section 10 (three
items: sidecar ready-timeout, native menu/dock integration with an in-app
workspace switcher, multi-window support). This doc covers the technical
approach for implementing them in `packages/desktop/src-tauri`.

## 2. Sidecar ready-timeout

`SidecarHandle::wait_for_ready` currently blocks forever reading the
child's stdout line-by-line. Move the read loop onto a spawned thread that
sends each parse attempt's outcome over an `mpsc::channel`; the caller
does `rx.recv_timeout(Duration)` instead of blocking directly on I/O.

- Default timeout: 30s. Overridable via `ZERO_SIDECAR_READY_TIMEOUT_SECS`
  env var (parsed as `u64` seconds) so tests can use a short timeout
  without sleeping 30s.
- On timeout: kill the child (`Child::kill`), drain/capture whatever
  stderr is available, and return `Err(String)` - the same shape the
  existing early-exit path already returns. `lib.rs`'s caller doesn't
  need to change: the failure dialog + `std::process::exit(1)` path
  already handles any `Err` from `wait_for_ready` identically, whether
  the sidecar exited early or hung.
- Test: spawn a real child process that never writes to stdout (e.g. a
  `sleep`-equivalent), call `wait_for_ready` with a short env-var
  timeout, assert `Err` and that the child no longer exists.

## 3. Native menu + multi-window (combined)

Per design discussion, "File > Open Folder..." always opens a **new**
window against a newly-picked workspace rather than replacing the
current one - this is both the workspace-switch affordance and the
multi-window feature, implemented as one change.

### 3.1 State model

Replace:
```rust
struct SidecarState(Mutex<Option<sidecar::SidecarHandle>>);
```
with:
```rust
struct SidecarState(Mutex<HashMap<String, sidecar::SidecarHandle>>);
```
keyed by window label. `kill_sidecar(app, label)` removes and kills only
that entry. `ExitRequested` (Cmd+Q/Dock quit) drains and kills every
entry in the map, not just one.

### 3.2 Window labels

`"main"` for the first window opened at launch. Subsequent windows opened
via the menu get `"workspace-{n}"`, `n` from a process-lifetime
`AtomicU32` counter starting at 1. Label generation is a small pure
function, unit-tested directly.

### 3.3 Menu

Build via `tauri::menu` (`Menu`, `Submenu`, `MenuItem`) in a new
`menu.rs`: a "File" submenu with "Open Folder..." (accelerator `CmdOrCtrl+O`).
Its handler re-runs the same folder-picker-then-spawn path used at first
launch (extracted into a shared function taking the `AppHandle`), passing
a freshly generated `workspace-{n}` label instead of `"main"`.

### 3.4 Remembered workspace

`save_remembered` still records a single path - whichever workspace was
most recently opened (first launch or any "Open Folder..." call) wins for
the *next app launch*. Multi-window is a within-run feature only; there is
no persisted "reopen all windows" behavior in this milestone.

### 3.5 Error handling

Unchanged per-window: a sidecar failure dialog + `std::process::exit(1)`
today kills the whole app even if other windows are healthy, because M8
only ever had one window. For M8.5, a failure spawning an *additional*
window (via the menu) must not take down other already-open windows -
show the dialog but only close/drop that one window's attempt, not
`process::exit`. The very first window (app launch) keeps today's
behavior (dialog + exit) since there's nothing else running yet to
preserve.

## 4. Testing

- Rust unit tests: ready-timeout behavior (`sidecar.rs`), window-label
  generation (`lib.rs` or a small new module).
- Manual smoke test additions to `packages/desktop/README.md`:
  - Hang the sidecar deliberately (e.g. rename the sidecar binary) and
    confirm the app shows the failure dialog within the timeout instead
    of hanging.
  - Use File > Open Folder... to open a second workspace in a new
    window; confirm both windows work independently (edit/terminal/chat
    in each); close one, confirm the other keeps running; quit the app,
    confirm both sidecars are gone (`ps`).
  - Relaunch: confirms the most-recently-opened-of-the-two workspace
    reopens automatically.

## 5. Out of scope (unchanged)

Auto-update, cross-platform builds, plugin worker isolation, cloud
provider auth/sync - see section 10 of the M8 design doc.
