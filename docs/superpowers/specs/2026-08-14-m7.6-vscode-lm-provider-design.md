# M7.6: Zero VS Code Plugin - Language Model API Registration

Date: 2026-08-14
Status: Approved

Per the roadmap (`docs/superpowers/specs/2026-08-04-zero-design.md` section
13) and M7.5a's deferral note, M7.5's remaining scope was "Copilot
custom-model auto-configuration" and "Language Model API registration."
Research (VS Code's `vscode.lm` API docs, the
`chat-model-provider-sample` extension, and the "AI language models in VS
Code" doc) found these are not two separate integrations: registering a
`vscode.LanguageModelChatProvider` is *how* a model appears in Copilot
Chat's model picker (via "Manage Models"). The alternative surface -
`github.copilot.chat.customOAIModels` / the newer `chatLanguageModels.json`
"Custom Endpoint" config - is a parallel, user-authored path for pointing
at arbitrary HTTP endpoints without writing an extension; it's deprecated
in favor of provider registration where a real extension is available, and
building an auto-writer for it would maintain a second, weaker integration
alongside the first for no benefit. So this milestone implements one
mechanism, `vscode.lm.registerLanguageModelChatProvider`, which satisfies both
named roadmap items.

## 1. Scope

### In scope

- **`ChatModelProvider`** (`@zero/vscode`, implements `vscode.
  LanguageModelChatProvider`): registers Zero as a chat model provider via
  `vscode.lm.registerLanguageModelChatProvider('zero', provider)` at activation,
  reusing the same `DaemonClient`/`DaemonInfo` (host, port, api key) that
  `GatewayCompletionProvider` already uses.
- **`package.json` additions**: `contributes.languageModelChatProviders`
  (static vendor declaration, required for the picker to show an entry
  before the provider is queried) and an `engines.vscode` bump to `^1.104`
  (from `^1.90.0` - `registerLanguageModelChatProvider`/`LanguageModelChatProvider`
  don't exist before that version). `@types/vscode` bumps to match.
- **`GET /health` extension** (`packages/daemon/src/modelGateway.ts`): adds
  `supportsTools: boolean`, computed from whichever provider `gateway.
  pick()` currently resolves to. One-line addition to an existing,
  deliberately-unauthenticated, status-only endpoint - no new daemon
  surface.
- **Anthropic-message translation** in `ChatModelProvider`, reusing `/v1/
  messages` (already SSE-streaming, Anthropic-shaped, and round-trips
  `tool_use`/`tool_result` blocks per `packages/core/src/
  anthropicTranslate.ts` - the same endpoint `zero claude` already drives):
  - `LanguageModelChatMessage[]` → Anthropic `messages` array; `
    LanguageModelToolCallPart` → `{type: "tool_use", id, name, input}`; `
    LanguageModelToolResultPart` → `{type: "tool_result", tool_use_id,
    content}`.
  - `options.tools` (`LanguageModelChatTool[]`) → Anthropic `tools: [{name,
    description, input_schema}]`.
  - SSE response parsing: text deltas → `progress.report(new
    LanguageModelTextPart(...))`; `tool_use` content blocks (buffered
    across `content_block_start` → accumulated `input_json_delta` →
    `content_block_stop`, keyed by block index) → `progress.report(new
    LanguageModelToolCallPart(id, name, JSON.parse(accumulatedJson)))`.
- **Dynamic tool-calling capability**: `provideLanguageModelChatInformation`
  calls `/health` and sets `capabilities.toolCalling` from `
  supportsTools`, so Copilot Chat only offers tool use to Zero when the
  currently-picked backend provider actually supports it (today: `true` for
  the daemon-side `NanoBridgeProvider`/`OpenAICompatProvider`, `false` for
  the browser-only `ChromeNanoProvider` used by Zero Lite's chat path -
  real, existing variance in `@zero/core`, not hypothetical).
- **Status bar integration**: extend the existing status bar item (from
  M7.5a) to reflect whether the LM provider is currently registered and
  reachable, reusing the same "daemon not found"/"no model available"
  states.

### Out of scope (explicit)

- Auto-writing `chatLanguageModels.json` / `github.copilot.chat.
  customOAIModels` - superseded by provider registration (see above).
- Auto-enabling Zero in the model picker. VS Code requires the user to
  open "Manage Models" and explicitly enable a third-party provider's
  models once (a trust/consent step, not something an extension can
  bypass) - this milestone ships the provider; the README documents the
  one-time manual enable step.
- Vision/image input (`capabilities.imageInput`) - no current `@zero/core`
  provider supports it.
- The extension executing tools itself. VS Code/Copilot Chat owns tool
  execution; `ChatModelProvider` only relays `tool_use` requests out and `
  tool_result` responses back in, exactly as `/v1/messages` already does
  for `zero claude`.
- Live-updating `capabilities.toolCalling` mid-session if the backend
  provider changes between VS Code's calls to `
  provideLanguageModelChatInformation` (e.g. Nano host disconnects
  mid-chat, gateway falls back to a non-tool provider). VS Code re-queries
  this periodically (model picker open, `silent` background refresh); a
  request landing on a provider that doesn't match the last-advertised
  capability is a known, accepted limitation - not solved with a push
  protocol this milestone.
- Chat participants (`@zero`-style slash commands) or a Zero-branded chat
  UI - this milestone only makes Zero selectable as a *model* inside
  existing chat surfaces (Copilot Chat, VS Code's built-in chat).
- Marketplace publishing (unchanged from M7.5a).

## 2. Decisions (from design session)

| Topic | Choice |
|---|---|
| Mechanism | `vscode.lm.registerLanguageModelChatProvider` only - covers both roadmap items |
| Wire format | Reuse `/v1/messages` (Anthropic-shaped SSE), no new gateway endpoint |
| Tool calling | Supported, gated by a new `/health.supportsTools` field per current backend |
| Tool execution | VS Code/Copilot Chat's responsibility, not the extension's |
| `engines.vscode` | Bumped to `^1.104` (required by the LM provider API) |
| Manual enable step | Accepted; documented, not automated (VS Code trust model) |
| Capability staleness | Accepted as a known limitation, no live-push fix this milestone |

## 3. Architecture

```
VS Code extension (packages/vscode)                    Daemon (packages/daemon)
─────────────────────────────────                      ────────────────────────
activation
  │
  ├─ DaemonClient.ensureRunning()  (reused from M7.5a)
  │
  ├─ vscode.lm.registerLanguageModelChatProvider('zero', ChatModelProvider)
  │                                                      │
  │   provideLanguageModelChatInformation({silent}) ─────┼──► GET /health
  │     ← { id, name, capabilities: { toolCalling } }    │      + supportsTools (new)
  │                                                      │      = gateway.pick()?.supportsTools()
  │   provideLanguageModelChatResponse(model, messages,  │
  │     options, progress, token)                        │
  │     → translate messages/tools to Anthropic shape ───┼──► POST /v1/messages (unchanged)
  │     → parse SSE stream                                │      → ProviderGateway.pick()
  │        text delta       → LanguageModelTextPart       │      → ChatCapableProvider.chat()
  │        tool_use block   → LanguageModelToolCallPart   │      → SSE (text/tool_use deltas)
  │                                                      │
  └─ status bar item ◄── EngineStatus + LM provider state
```

`/v1/messages` is unchanged except for the `/health` addition; the same
endpoint now serves `zero claude` (M7), and both Zero's own extension and
Copilot Chat (M7.6) as consumers.

## 4. `ChatModelProvider`

Implements `vscode.LanguageModelChatProvider`:

- `provideLanguageModelChatInformation({silent}, token)`: `GET /health`
  against the daemon discovered via `DaemonClient`. No daemon or no model
  available → return `[]` (Zero disappears from the picker rather than
  showing a broken entry - "degrade the failing subsystem only"). Model
  available → return one `LanguageModelChatInformation` entry (`id: "zero"`,
  `family: "zero"`, `maxInputTokens`/`maxOutputTokens` from the picked
  provider's `capabilities()`, `capabilities: { toolCalling: health.
  supportsTools }`).
- `provideLanguageModelChatResponse(model, messages, options, progress,
  token)`: builds the Anthropic request body (section 1), `POST /v1/
  messages` with the `x-api-key` header from `DaemonInfo`, reads the
  response body as SSE (`ReadableStream` reader, split on blank lines,
  parse `event:`/`data:` pairs - no library, same shape the daemon already
  emits), and reports parts incrementally. `token` cancellation aborts the
  underlying `fetch` via a wired `AbortController`, matching `
  inlineCompletion.ts`'s existing cancellation pattern.
- `provideTokenCount(model, text, token)`: `Math.ceil(chars / 4)` per
  `CLAUDE.md`'s token-estimate convention - no new estimation logic.

## 5. `@zero/vscode` package layout (additions)

```
packages/vscode/
  package.json                    # + contributes.languageModelChatProviders, engines.vscode bump
  src/
    chatModelProvider.ts           # LanguageModelChatProvider implementation
    anthropicSse.ts                # SSE reader/parser shared by chatModelProvider (fetch Response -> events)
    *.test.ts                      # beside each, injected vscode + fetch fakes
```

`anthropicSse.ts` is split out from `chatModelProvider.ts` because it's the
one genuinely new piece of wire-format logic this milestone adds (parsing,
not just calling, an SSE stream) and is independently testable against
canned SSE payloads without any `vscode` API surface.

## 6. Error handling and degradation

Consistent with M7.5a and `CLAUDE.md`'s "degrade the failing subsystem
only" constraint:

- No daemon found: `provideLanguageModelChatInformation` returns `[]` -
  Zero simply isn't offered as a model; no error dialogs.
- Daemon running, no model available (`/health` 503-equivalent state):
  same `[]` result.
- Mid-response failure (daemon dies, network error): the SSE read loop
  surfaces the daemon's `event: error` payload (already emitted by `/v1/
  messages` today) by rejecting the promise `provideLanguageModelChatResponse`
  returns; VS Code surfaces that as a failed chat turn, not a crash.
- Tool calls requested but the picked provider doesn't actually support
  them (capability staleness, section 1): the request still includes `
  tools` in the body (matching `/v1/messages`'s existing behavior for `
  zero claude`, unchanged here) - a non-tool-capable provider either
  ignores them or the response has no `tool_use` blocks; no special-casing
  needed since the wire format already handles "zero tool calls in the
  response" as the default case.

## 7. Testing

- `packages/vscode/src/chatModelProvider.test.ts`: injected `vscode`
  fakes (message/tool part construction, cancellation token) and a fake
  `fetch` returning canned SSE bodies - covers text-only responses,
  tool-call responses (single and multiple `tool_use` blocks), `[]` when
  no daemon/model, and cancellation mid-stream.
- `packages/vscode/src/anthropicSse.test.ts`: pure parser tests against
  hand-written SSE payloads (message_start/content_block_*/message_stop
  sequences, including malformed/partial chunks split across reads).
- `packages/daemon/src/modelGateway.test.ts`: add a case asserting `/health`
  includes `supportsTools` matching `gateway.pick()`'s provider.
- Manual verification (no automated VS Code integration harness, same as
  M7.5a): sideload the `.vsix`, run "Chat: Manage Models" in VS Code,
  enable Zero, confirm it's selectable in Copilot Chat's model picker,
  confirm both a plain text turn and a tool-using turn (e.g. asking it to
  read a file, backed by an Ollama model with tool calling) work, and
  confirm the model disappears from the picker with the daemon stopped.
