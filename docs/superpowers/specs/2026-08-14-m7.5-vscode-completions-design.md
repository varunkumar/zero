# M7.5a: Zero VS Code Plugin - Inline Completions

Date: 2026-08-14
Status: Approved

Per the roadmap (`docs/superpowers/specs/2026-08-04-zero-design.md` section
13), M7.5 is: inline completion provider over the gateway, Copilot
custom-model auto-configuration, Language Model API registration, daemon/
Nano-host autostart per section 10. This spec narrows M7.5 to its first,
best-understood slice: **inline completions only**. Copilot custom-model
config and Language Model API registration depend on VS Code/Copilot
extension surfaces whose exact shape isn't verified yet and carry
independent research risk; they become their own follow-up milestone
(M7.6+) once that's known, rather than blocking this one.

## 1. Scope

### In scope

- **New package** `packages/vscode` (`@zero/vscode`): a VS Code extension
  providing offline/local inline completions, structured like the other
  workspace packages.
- **`POST /v1/complete`** on the model gateway (`packages/daemon/src/
  modelGateway.ts`): a new, non-streaming endpoint alongside the existing
  `/v1/messages`. Takes `{ prefix, suffix, path }`, routes through the same
  `ProviderGateway`/`ChatCapableProvider` stack used by chat (wrapping the
  FIM prompt as a single user turn under the hood), returns `{ text }`.
- **`GatewayCompletionProvider`** (`@zero/vscode`, implements `@zero/core`'s
  `ModelProvider`): HTTP client for `/v1/complete`.
- **`VscodeBufferContext`** (`@zero/vscode`, implements `ContextProvider`):
  feeds open-tab content from `vscode.workspace.textDocuments` into
  `@zero/core`'s existing `BufferContext` shape (`{path, content}` pairs) -
  no new context-gathering logic, just an adapter over VS Code's document
  API.
- **`DaemonClient`** (`@zero/vscode`): health-checks a local daemon and, if
  none is found, spawns one (`zero serve --gateway-port <port>` via
  `child_process`), assuming the `zero` CLI is installed and on `PATH`.
- **`InlineCompletionItemProvider` registration**: wires `CompletionEngine`
  + `CompletionScheduler` (both from `@zero/core`, unchanged) into VS
  Code's inline completion API, using the project's standard 150ms
  keystroke debounce / one-request-in-flight rule.
- **Status bar item**: reflects `CompletionEngine`'s `EngineStatus`
  (`activeModel`/`reason`) plus a distinct "daemon not found" state,
  matching the "degrade the failing subsystem only, never break editing"
  constraint - the editor stays fully usable with completions off.
- **Packaging**: `.vsix` build via `vsce`, sideload only (not published to
  the VS Code Marketplace in this milestone).

### Out of scope (explicit)

- Copilot custom-model auto-configuration (`github.copilot.chat.
  customOAIModels` or equivalent) - deferred to a follow-up milestone once
  the actual configuration surface is verified.
- VS Code Language Model API registration (`vscode.lm.*`) for built-in
  chat/other extensions - same reason, deferred.
- Chat/agent mode inside VS Code.
- Daemon-launched or automated Chrome Nano-host attachment. Same decision
  as M7: reuse an already-open Zero tab only. If no Nano host is attached,
  the gateway falls back to whatever `ChatCapableProvider` the
  `ProviderGateway` picks next (e.g. Ollama-backed), or reports "no model
  available" - the extension does not manage Chrome.
- Bundling the daemon inside the extension. Requiring the `zero` CLI on
  `PATH` is a deliberate simplification; a fully self-contained install is
  M8 (Zero IDE, Tauri + bundled daemon) territory.
- Marketplace publishing.
- Streaming completions. `/v1/complete` is non-streaming by design: ghost
  text needs the full completion before it renders, and completions are
  short, so streaming buys nothing here (unlike chat's SSE path).

## 2. Decisions (from design session)

| Topic | Choice |
|---|---|
| Milestone scope | Narrow to inline completions; Copilot/LM API become M7.6+ |
| Reaching a model | New `/v1/complete` gateway endpoint, not chat-endpoint reuse |
| Nano host | Reuse-only, same as M7 - no automated launch |
| Daemon discovery | Require `zero` CLI on `PATH`; spawn `zero serve` if not running |
| Streaming | Non-streaming `/v1/complete`; completions are short and need to land whole |
| Distribution | `.vsix` sideload only, no Marketplace publish this milestone |

## 3. Architecture

```
VS Code extension (packages/vscode)                  Daemon (packages/daemon)
─────────────────────────────────                    ────────────────────────
activation
  │
  ├─ DaemonClient.ensureRunning()
  │    health-check 127.0.0.1:<port>/health
  │    not running? spawn `zero serve --gateway-port <port>`
  │                                                    │
  ├─ registerInlineCompletionProvider                  │
  │    CompletionEngine(                               │
  │      providers: [GatewayCompletionProvider] ───────┼──► POST /v1/complete (new)
  │      context: [VscodeBufferContext]                │      { prefix, suffix, path }
  │    )                                                │      → ProviderGateway.pick()
  │    CompletionScheduler (150ms debounce,             │      → ChatCapableProvider.chat()
  │      one request in flight)                         │        (single user turn, FIM prompt)
  │                                                      │      → { text } (non-streaming)
  └─ status bar item ◄── EngineStatus (activeModel/reason)
```

`GatewayCompletionProvider.complete()` satisfies `ModelProvider`'s
`AsyncIterable<string>` return by yielding the single `/v1/complete`
response as one chunk - `CompletionEngine` just accumulates chunks, so a
one-item iterable is a legal, if degenerate, implementation.

`/v1/complete` is additive: `/v1/messages` and its SSE path are untouched.
Both endpoints share `opts.gateway` (`ProviderGateway`), so completions get
the same Nano-bridge/Ollama fallback chat already gets, for free.

## 4. `POST /v1/complete`

- Request: `{ prefix: string; suffix: string; path: string }`.
- Auth: same `x-api-key` header check as `/v1/messages` (loopback-bound,
  but not deliberately unauthenticated like `/health`).
- Behavior: builds a single-user-turn `ChatMessage[]` from the FIM prompt
  (reusing whatever prompt-building `@zero/core` already has for FIM, e.g.
  `buildFimPrompt`, adapted for the chat-shaped `ChatCapableProvider`
  interface rather than the raw `ModelProvider.complete()` interface used
  client-side today), calls `opts.gateway.pick()` then `.chat(messages,
  undefined, signal)`, accumulates deltas (no tool calls expected/handled),
  and returns `{ text }` once the stream ends.
- No model available: `503`, matching `/v1/messages`'s existing behavior.
- Errors: `400` on malformed body, matching `/v1/messages`.

## 5. `@zero/vscode` package layout

```
packages/vscode/
  package.json           # VS Code extension manifest (engines.vscode, activationEvents, contributes)
  src/
    extension.ts          # activate()/deactivate(), wires everything below
    daemonClient.ts        # DaemonClient: health-check + spawn
    gatewayCompletionProvider.ts   # ModelProvider over /v1/complete
    vscodeBufferContext.ts # ContextProvider adapter over vscode.workspace.textDocuments
    inlineCompletion.ts    # InlineCompletionItemProvider registration + scheduler wiring
    statusBar.ts           # status bar item driven by EngineStatus
    *.test.ts              # beside each module, injected vscode fakes
```

Depends on `@zero/core` (workspace dependency, same as `packages/web` and
`packages/daemon`). No dependency on `@zero/protocol` or `@zero/daemon` -
the extension only talks to the gateway over plain HTTP, the same
boundary `zero claude`'s Anthropic client crosses.

## 6. Error handling and degradation

Per `CLAUDE.md`'s constraint ("editor must stay fully usable when no model
is available - degrade the failing subsystem only"):

- No daemon found and spawn fails (e.g. `zero` not on `PATH`): status bar
  shows "Zero: daemon not found - install the zero CLI", inline completions
  silently produce nothing (no error popups on every keystroke).
- Daemon running, gateway returns 503 (no model): status bar shows "Zero:
  no model available", same silent no-op behavior.
- Daemon running, Nano host not attached but Ollama available: gateway
  falls back automatically (existing `ProviderGateway` behavior); status
  bar shows the active fallback provider's id.
- Request timeout/abort (fast typing): `CompletionScheduler`'s existing
  one-in-flight-cancels-previous behavior applies unchanged.

## 7. Testing

- `packages/vscode/src/*.test.ts`: dense unit coverage with injected fakes
  for `vscode.*` APIs (document content, position, cancellation tokens) and
  a fake `fetch` for `GatewayCompletionProvider` - no real VS Code host or
  daemon process in unit tests, matching `@zero/core`'s existing style.
- `packages/daemon/src/modelGateway.test.ts`: add cases for `/v1/complete`
  - happy path, 503 no-model, 400 malformed body, 401 bad key - alongside
  the existing `/v1/messages` cases.
- Manual verification (this milestone has no automated VS Code
  integration-test harness): sideload the `.vsix` in a real VS Code/Cursor
  window, confirm ghost text appears with a running daemon + attached Nano
  tab or Ollama, and confirm graceful degradation with the daemon stopped.

## 8. Out-of-scope follow-ups (not this milestone)

- M7.6+: Copilot custom-model auto-configuration and/or Language Model API
  registration, once their actual VS Code extension surfaces are verified.
- Automated Nano-host launch (shared open item with M7).
- Marketplace publishing.
