# M1.5 Editor Shell — Design

Turns the minimal M0 web shell (`packages/web/src/App.tsx`: one open file, fixed
sidebar, flat `useState`) into a VS Code-class editor UI. Per the roadmap
(`docs/superpowers/specs/2026-08-04-zero-design.md` section 12), this gets its
own design session before implementation; this document is that session's
output.

## 1. Scope

In scope: workbench layout (resizable/collapsible panes, split editors),
editor tabs with dirty indicators, command palette, fuzzy file opener
(Cmd/Ctrl+P), global search panel, virtualized file tree with file icons,
keybinding system, light and dark themes, status bar, settings UI.

Out of scope (explicitly deferred): keybinding rebinding UI, VS Code theme
JSON import, drag-and-drop tab reordering as a build target (accepted as a
side effect of the layout library, not tested), regex/glob search (literal
substring search only).

## 2. Deviation from the roadmap's "UI only" note

The roadmap line for M1.5 says "no new daemon capabilities." In practice two
small additions are unavoidable and were explicitly approved during design:

- A global search panel needs to search file *contents* across the project.
  The daemon only exposes `fs/read`/`fs/write`/`fs/tree` — there is no way to
  implement content search without either reading every file over the wire
  (client-side search) or adding a daemon-side search RPC. **Decision: add a
  minimal `fs/search` RPC** rather than the client-side fallback, for
  performance on larger projects.
- Settings (theme, layout, open tabs) need to persist. **Decision: persist to
  both `localStorage` (instant paint, no daemon round trip) and a daemon-backed
  `settings/get`/`settings/set` RPC** backed by `.zero/settings.json`, so
  preferences survive across browsers/machines for the same workspace.

Both additions follow the existing `Workspace` class's safety patterns (path
containment, symlink-safety, `.gitignore` respect) rather than introducing a
new access path.

## 3. Module architecture

New code lives under `packages/web/src/workbench/`, each module independently
testable with fakes, wired together in a new `Workbench.tsx` that replaces the
body of `App.tsx` (connection bootstrapping in `App.tsx` is unchanged):

- `layout/` — dockview integration: panel/group registry, layout
  serialization for persistence.
- `tabs/` — editor-tab state machine: open tabs, active tab, dirty flags,
  per-tab buffer/viewState. Independent of dockview so it's unit-testable
  without mounting it.
- `commands/` — a command registry (`{ id, title, run, keybinding? }`) that
  the palette, keybindings, and status bar/menu all read from — single source
  of truth so a keybinding and its palette entry can't drift apart.
- `keybindings/` — `tinykeys`-based dispatcher resolving key events to
  command IDs via the registry's declared defaults.
- `search/` — global search panel, talks to `fs/search`.
- `theme/` — CSS-variable theme definitions + a `ThemeProvider` toggling a
  `data-theme` attribute.
- `settings/` — settings UI + persistence (localStorage cache + daemon file,
  see section 5).
- `filetree/` — `react-arborist` wrapper over `fs/tree` data.

## 4. New dependencies

| Package | Purpose | Why this one |
|---|---|---|
| `dockview-react` | workbench layout: resizable/collapsible panes, split editors, tab groups | actively maintained, purpose-built VS Code-style docking; avoids hand-rolling split-pane/drag logic |
| `cmdk` | command palette + fuzzy file opener | small headless primitive (~3kb), handles keyboard nav/filtering, same building block used by Linear/Vercel-style palettes |
| `command-score` | fuzzy ranking for the file opener | the tiny scorer `cmdk` itself uses internally; avoids a second heavier fuzzy-match dependency |
| `react-arborist` | virtualized file tree | purpose-built virtualized tree with keyboard nav and renderer customization |
| `tinykeys` | keybinding dispatch | ~500 bytes, no dependencies, exactly the "match key combo to handler" primitive needed |

No new dependency for themes (CSS variables), status bar, or settings UI —
these are small enough to hand-roll.

## 5. Daemon API additions

### `fs/search`

Request: `{ query: string, caseSensitive?: boolean }`
Response: `{ matches: { path: string, line: number, column: number, text: string }[], truncated: boolean }`

Implementation in `Workspace`: reuse `tree()` + the ignore rules to enumerate
non-ignored files, skip binary files (null-byte sniff on the first chunk),
skip files over 1MB, read each as UTF-8, do a literal substring scan per line
(no regex in M1.5). Cap total matches (500); set `truncated: true` when the
cap is hit so the UI can say "showing first 500 matches."

### `settings/get` / `settings/set`

Request/response:
- `settings/get`: `{ key: string }` → `{ value: unknown }`
- `settings/set`: `{ key: string, value: unknown }` → `{}`

Backed by a single JSON file `.zero/settings.json` in the workspace root,
created on first write, read/written whole-file (settings are small: layout
state, theme, open tabs). `.zero/` is added to the default ignore set (same
mechanism as `.git`) so it never appears in the file tree or search results.

### Client persistence flow

On boot, the client reads a `localStorage` cache immediately (before the
daemon connection resolves) so the UI paints with last-known layout/theme
with no flash. Once connected, it requests `settings/get("workbench")` and
reconciles: the daemon value wins on conflict, and `localStorage` is updated
to match. Every layout/theme/tab change writes to `localStorage` synchronously
and to `settings/set` debounced ~500ms.

## 6. Workbench layout & tabs

`dockview-react` provides the outer shell: a left sidebar panel group (file
tree, search panel, switchable via an icon rail) and a main editor area
supporting horizontal/vertical splits (multiple groups).

Tabs are **not** dockview's native tab UI bound directly to files. `tabs/`
owns the source of truth (`{ id, path, dirty, viewState }[]` per group); a
thin adapter renders that state into dockview panels, keeping tab logic
testable without mounting dockview.

A tab is dirty when its buffer content differs from last-saved content
(reuses the existing buffer/save flow from `App.tsx`, moved into `tabs/`).
Closing a dirty tab shows a small inline `<ConfirmBar>` in the tab itself, not
a modal.

Sidebar and panel groups are resizable and collapsible (dockview native);
collapsed/expanded state and sizes persist via section 5's mechanism. No
drag-and-drop tab reordering is a build target — dockview's default behavior
is accepted as-is, untested.

## 7. Command palette, fuzzy file opener, search panel

Command palette (`Cmd/Ctrl+Shift+P`) and fuzzy file opener (`Cmd/Ctrl+P`)
share one `<Palette>` shell component (overlay, input, list, keyboard nav),
parameterized by data source:
- Palette: `cmdk`'s built-in filtering over the `commands/` registry.
- Opener: `fs/tree` results ranked by `command-score` against the query.

The global search panel lives docked in the sidebar (not an overlay, since
results need to stay visible while browsing): a text input debounced ~200ms
calling `fs/search`, results grouped by file; clicking a result opens that
file/tab and scrolls to the line.

## 8. File tree

`react-arborist` fed by `fs/tree`'s flat `{path, kind}[]`, converted to
arborist's nested node shape once and memoized. File icons: a small static
extension→icon map (monochrome SVGs for common extensions: ts/js/json/md/
css/img/default) — no external icon-theme dependency. The tree re-fetches
`fs/tree` (debounced) on any `fs/changed` event under a watched directory, so
added/removed files/dirs show up, not just content changes.

## 9. Keybindings

`tinykeys` maps key combos to command IDs declared by the `commands/`
registry's default bindings, Cmd/Ctrl-aware (Cmd on Mac, Ctrl elsewhere).
Fixed defaults only — no rebinding UI in M1.5.

## 10. Themes

Two CSS variable sets under `:root[data-theme="light"]` /
`[data-theme="dark"]`, named after the area they affect (`--zero-editor-bg`,
`--zero-sidebar-bg`, `--zero-statusbar-bg`, `--zero-tab-*`, `--zero-accent`,
etc.). Toggled via a command + status bar control; persisted via section 5.

## 11. Status bar & settings UI

Status bar extends the existing thin bar in `App.tsx` into a real row:
current file path, cursor line/col (from CodeMirror selection state), the
existing completion engine status pill (reused as-is), theme toggle.

Settings UI is a simple panel (not a form-builder) covering what exists in
M1.5: theme choice, and a read-only list of active keybindings (for
discoverability, without needing a rebinding UI). Opened via the command
palette entry "Preferences: Open Settings."

## 12. Testing

Per project convention (dense unit coverage with fakes, colocated
`*.test.ts(x)`):

- `tabs/`, `commands/`, `keybindings/`, and the client-side settings-merge
  logic are pure state machines: unit-tested without mounting dockview/cmdk
  or touching the DOM.
- Daemon: `fs/search` and `settings/get`/`set` get integration tests against
  real temp dirs, matching the existing `Workspace` test style — search
  correctness (case sensitivity, ignore respect, truncation cap), settings
  round-trip and file creation.
- Protocol: schema round-trip tests for the two new RPC shapes, following
  `messages.test.ts` conventions.
- A few new Playwright E2E flows: open two files and split the editor, use
  the command palette to close a tab, use Cmd+P to open a file, run a global
  search and jump to a result.
