# M5.1: CLI polish (global command, TUI, global sessions/settings)

Date: 2026-08-09

## Context

M5 ([spec](2026-08-07-m5-zero-agents-design.md)) landed headless `zero agent
"task"`, per-workspace session storage at `<workspace>/.zero/sessions`, and
per-workspace settings at `<workspace>/.zero/settings.json`. Using it in
practice surfaced four gaps against expectations set by the design doc and
by comparable tools (Claude Code CLI in particular):

1. `zero` only runs via `bun run` from inside this repo, not as a `zero`
   command from any directory.
2. There's no interactive TUI — `zero agent` is one-shot only, and
   approval/session-management happens through a bare `y/N` readline
   prompt.
3. Sessions are stored inside the workspace itself
   (`<workspace>/.zero/sessions`), not somewhere a user can inspect/manage
   independent of any one project.
4. Settings are similarly workspace-local, not global.

This spec covers `@zero/daemon` only — no `@zero/core` or `@zero/protocol`
changes.

## 1. Command surface (aligned with Claude Code's CLI)

Today `zero` (bare) starts the web daemon and `zero agent "task"` runs
headless. This is inverted to match the mental model of `claude` / `claude
--resume` / `claude -p`, where the bare command is the interactive tool and
scripting is an explicit flag:

| Command | Behavior |
|---|---|
| `zero [path]` | **New.** Launches the TUI (§2), starts a new chat session rooted at `path` (default cwd). Requires stdin/stdout to be a TTY. |
| `zero --resume [path]` | **New.** TUI session picker scoped to `path`'s project (§2, §3) → resumes the selected session into the chat screen. |
| `zero -p "task" [--yes] [--session <id>] [path]` | **Renamed** from `zero agent "task" ...`. Same headless, single-shot behavior as M5 — unchanged otherwise. `-p`'s value is the task text (a flags-with-value entry, like `--session`). |
| `zero serve [path] [--gateway-port N]` | **Renamed** from bare `zero`. Today's web daemon (editor/terminal/chat over HTTP/WS on :4820) — unchanged behavior. |

This is a breaking change to `zero`'s bare invocation and drops the `agent`
subcommand name. Called out explicitly in the PR description; there are no
external users of M5 yet (it landed this session), so no deprecation shim.

`bin/zero.ts` dispatch becomes: `serve` as first token → web daemon path
(today's bare-`zero` code, verbatim); otherwise → TUI/headless path,
branching on whether `-p` is present.

## 2. TUI

New dependency: `ink` (React for CLIs) + `ink-testing-library` (dev). New
directory `packages/daemon/src/cli/tui/`.

- `App.tsx` — top-level component, one of two modes:
  - **Picker mode** (`--resume`): lists sessions for the current project
    (§3) newest-first via `SessionStore.list()`, arrow keys + enter to
    select, or "new session". Selecting transitions to chat mode.
  - **Chat mode** (default): renders the transcript (assistant text
    streamed token-by-token, `[tool] name(args)` lines, `[result]` lines)
    below a scrolling history, a text input at the bottom for the next
    user message, and — when an `approvalRequest` event arrives — an
    inline panel with the diff/command preview and a `y/n` prompt that
    calls `runtime.resolveApproval` on keypress, blocking further input
    until resolved.
  - Drives the same `AgentRuntime.sendMessage` async generator the
    headless path uses; TUI vs. headless differ only in how `TurnEvent`s
    are rendered and how approval is resolved (keypress vs. readline).
  - Multi-turn: after a turn completes (generator exhausted), the input
    box re-enables for the next message in the same session, looping
    until the user quits (`Ctrl+C` / `Esc`).
- If stdin or stdout isn't a TTY, `zero` (bare) and `zero --resume` print
  `"zero requires an interactive terminal; use zero -p \"task\" --yes for
  scripting"` and exit 1 — no partial/degraded TUI render.

## 3. Sessions move to `~/.zero/sessions/<project>/`

New `packages/daemon/src/paths.ts`:

- `zeroHome()`: `process.env.ZERO_HOME ?? join(homedir(), ".zero")` — the
  env override exists so tests never touch a real `~/.zero`.
- `sanitizeWorkspacePath(root: string)`: absolute path with `/` (and, on
  Windows, `\`) replaced by `-` (e.g. `/Users/x/projects/zero` →
  `-Users-x-projects-zero`) — same convention already used for this
  session's own scratchpad path, so it's a proven-safe, human-legible
  scheme requiring no new collision handling.
- `sessionsDir(workspaceRoot: string)`: `join(zeroHome(), "sessions",
  sanitizeWorkspacePath(workspaceRoot))`.
- `settingsPath()`: `join(zeroHome(), "settings.json")`.

`SessionStore` changes constructor from `(workspace: Workspace)` to
`(workspaceRoot: string)` and computes `#dir()` via `sessionsDir(...)`
instead of `join(workspace.root, ".zero", "sessions")`. Call sites
(`main.ts`, `cli/agent.ts`) pass `ws.root` instead of `ws`.

No migration of existing `<workspace>/.zero/sessions` — M5 shipped this
session, so there are no real sessions to preserve. Noted in the PR
description as a clean break.

## 4. Settings move to `~/.zero/settings.json`

`Workspace#readSetting`/`#writeSetting`/`#readSettingsFile` (currently
reading/writing `<this.#root>/.zero/settings.json`) are repointed at
`settingsPath()` from `paths.ts` instead of `this.#root`. Global, no
per-project override. RPC method signatures (`settings/get`/`settings/set`
in `main.ts`) are unchanged — only where the file lives changes.

## 5. Global install

New `scripts/install.sh` (bash, repo root):

1. Requires `bun` on `PATH` (fails fast with a clear message if missing).
2. `bun install` at the repo root — installs all workspace deps and
   compiles `node-pty`'s native addon for the current platform, so `pty/*`
   RPCs and `zero serve`'s terminal panel work out of the box.
3. `mkdir -p ~/.local/bin`.
4. Writes an executable wrapper to `~/.local/bin/zero`:
   ```sh
   #!/usr/bin/env bash
   exec bun run "<absolute-path-to-repo>/packages/daemon/bin/zero.ts" "$@"
   ```
   with the absolute repo path substituted in at install time. This (not
   `bun link`) is deliberate: the wrapper always runs against this
   checkout's already-installed `node_modules` (including the compiled
   native addon), regardless of `cwd` at invocation time.
5. If `~/.local/bin` isn't on `PATH` (checked against `$PATH`), prints the
   line to add to the user's shell rc rather than silently leaving `zero`
   unreachable.

Idempotent — re-running overwrites the wrapper and re-runs `bun install`,
safe after a `git pull`.

## 6. Error handling

- TUI on a non-TTY: fails fast per §2, same "degrade don't hang" pattern
  M5 established for headless approval prompts.
- `paths.ts` functions are pure/sync path math — no new failure modes.
  `SessionStore`/settings I/O errors are unchanged from M5 (already
  handled: missing dir → empty list, missing file → `undefined` setting).
- Install script: `bun install` failures (e.g. `node-pty` native build
  failing on an unsupported platform) surface bun's own error output and
  a non-zero exit; the script does not swallow or reinterpret them.

## 7. Testing

- `packages/daemon/src/paths.test.ts`: `sanitizeWorkspacePath` on various
  inputs, `zeroHome()`/`sessionsDir()`/`settingsPath()` respecting
  `ZERO_HOME`.
- `sessions.test.ts`: updated to construct `SessionStore` with a
  `ZERO_HOME`-scoped tmpdir; add a case proving two different workspace
  roots produce disjoint session listings.
- `workspace.test.ts` (settings cases): updated to assert settings land
  under `ZERO_HOME`, independent of the workspace root passed to
  `Workspace`.
- `cli/agent.test.ts`: update flag from positional task + `agent` subcommand
  to `-p "task"`, per §1's renamed surface.
- New `cli/tui/App.test.tsx` using `ink-testing-library`: session picker
  renders and lists sessions, selecting "new" enters chat mode, an
  `approvalRequest` event renders the preview and `y`/`n` keypresses call
  `resolveApproval` with the right value, non-TTY exits 1 with the
  documented message.
- `scripts/install.sh`: `bash -n scripts/install.sh` (syntax check) as an
  automated check — the script itself isn't executed in CI since it
  mutates `~/.local/bin`/runs `bun install` against the real filesystem.
  Manual test steps (below) cover actually running it.

## 8. Manual test plan (for the PR description)

1. `./scripts/install.sh`, open a **new** shell, run `zero --help` (or any
   subcommand) from `$HOME` or `/tmp` — confirm it resolves and the
   workspace root defaults to that cwd.
2. `cd` into any git repo, run bare `zero` — TUI launches, type a message,
   confirm streamed text renders; trigger a write tool, confirm the
   approval panel shows a diff and `y`/`n` resolves it.
3. In the same repo, run `zero --resume` — confirm the session just
   created appears in the picker and resumes with its prior transcript.
4. Run `zero -p "say hi" --yes` — confirm it behaves exactly like M5's
   `zero agent "say hi" --yes` did (single-shot, exits 0).
5. Run `zero serve` — confirm the web daemon starts as before.
6. Inspect `~/.zero/sessions/<sanitized-project-path>/` and
   `~/.zero/settings.json` directly — confirm they exist and are
   human-readable JSON.
7. From a non-TTY context (e.g. `zero < /dev/null`), confirm the TUI
   refuses with the documented error instead of hanging.
